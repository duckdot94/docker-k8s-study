# 컨테이너 vs 가상 머신(VM)

> Week 1 - Day 1 개념 정리. 실습은 [README.md](README.md) 참고

## 한 줄 요약
- **VM**: 하드웨어를 흉내 내서 **OS 전체**를 따로 띄운다.
- **컨테이너**: 호스트 OS의 **커널을 공유**하고, 프로세스만 **격리**해서 띄운다.

## 구조 비교

```
        VM                                  컨테이너
┌─────────┐ ┌─────────┐          ┌─────────┐ ┌─────────┐
│  앱 A   │ │  앱 B   │          │  앱 A   │ │  앱 B   │
│ 라이브러리│ │ 라이브러리│          │ 라이브러리│ │ 라이브러리│
│ 게스트 OS│ │ 게스트 OS│          └────┬────┘ └────┬────┘
└────┬────┘ └────┬────┘          ┌─────┴───────────┴─────┐
┌────┴───────────┴────┐          │   컨테이너 런타임      │
│    하이퍼바이저      │          ├───────────────────────┤
├─────────────────────┤          │  호스트 OS (커널 공유)  │
│     호스트 OS        │          ├───────────────────────┤
├─────────────────────┤          │       하드웨어         │
│       하드웨어       │          └───────────────────────┘
└─────────────────────┘
```

## 비교표

| 항목 | VM | 컨테이너 |
|---|---|---|
| 격리 단위 | OS 전체 | 프로세스(+파일시스템, 네트워크 등) |
| 커널 | VM마다 자체 커널 | 호스트 커널 공유 |
| 크기 | 보통 수 GB | 보통 수십~수백 MB (nginx 이미지 261MB, ubuntu 179MB) |
| 시작 시간 | 분 단위(OS 부팅) | 초 단위 이하(프로세스 시작) |
| 자원 사용 | 무거움 | 가벼움 |
| 격리 강도 | 강함(커널까지 분리) | 상대적으로 약함(커널 공유) |
| 다른 OS 실행 | 가능(Windows 위에 Linux 등) | 호스트와 같은 종류의 커널만 가능 |

## 컨테이너 격리를 가능하게 하는 것 (Linux 기능)
- **namespace**: 프로세스가 보는 세계를 분리한다 (프로세스 목록, 네트워크, 호스트명, 파일시스템 등)
- **cgroups**: 사용할 수 있는 CPU, 메모리 양을 제한한다
- **이미지 레이어**: 읽기 전용 층을 쌓고, 컨테이너가 맨 위에 쓰기 층을 얹는다 (Day 2에서 자세히)

## 이미지와 컨테이너
- **이미지**: 실행에 필요한 파일을 담은 읽기 전용 설계도
- **컨테이너**: 이미지로 만든 실행 인스턴스. 안의 프로세스가 끝나면 컨테이너도 종료된다
- 컨테이너를 지워도 이미지는 남고, 컨테이너의 쓰기 층은 컨테이너와 함께 사라진다 (오늘 실험)

## Mac에서는 어떻게 동작하나
컨테이너는 Linux 커널 기능이라 macOS 커널에서는 직접 실행할 수 없다. 그래서 OrbStack, Docker Desktop 같은 도구가 **가벼운 Linux VM을 하나 띄우고 그 안에서 컨테이너를 실행**한다.

오늘 `docker logs web`에서 이 증거가 보였다.
```
[notice] 1#1: OS: Linux 7.2.12-orbstack-00394-gbecdd6130068
```
내 Mac은 macOS인데 nginx 컨테이너는 Linux 커널(OrbStack의 VM)에서 돌고 있다. 컨테이너끼리는 이 VM의 커널을 공유한다.

즉 Mac에서는 "VM 한 개 위에 컨테이너 여러 개"의 구조다. 컨테이너가 VM을 완전히 대체하는 게 아니라, **VM 안에서 앱 단위를 가볍게 나누는 도구**로 이해하면 된다.

## 언제 무엇을 쓰나
- **컨테이너가 유리**: 마이크로서비스, 빠른 배포와 확장, 개발/운영 환경 통일(CI/CD), 한 서버에 많은 앱
- **VM이 유리**: 강한 격리가 필요한 멀티테넌트, 다른 OS나 커널이 필요한 경우, 레거시 앱
- 실무에서는 둘을 함께 쓴다 (클라우드 VM 위에서 컨테이너를 실행, 쿠버네티스 노드도 보통 VM)

## 직접 확인해 볼 것
- [ ] 컨테이너 안에서 `uname -r`을 실행해 본다. Mac에서 실행한 `uname -r`과 값이 다른가? (컨테이너는 Mac이 아니라 Linux VM의 커널을 본다)
- [ ] 컨테이너 안의 `hostname`이 `docker ps`의 CONTAINER ID와 같은지 확인한다
- [ ] 컨테이너 안에서 `ps aux`를 실행해 본다. 프로세스가 몇 개 보이는가? (PID 1이 무엇인가?)
- [ ] `docker stats --no-stream`으로 실행 중인 컨테이너의 메모리 사용량을 확인한다. VM 하나를 띄울 때와 비교하면 어떤가?
