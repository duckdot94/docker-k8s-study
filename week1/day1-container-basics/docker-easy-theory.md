# 도커와 컨테이너, 쉽게 이해하기

> Week 1 개념 보충. 초등학생도 이해할 수 있게 비유로 정리했다. 기술적인 비교는 [container-vs-vm.md](container-vs-vm.md) 참고

## 1. 왜 도커가 필요할까?

친구에게 내가 만든 게임을 보내 줬는데 이런 말을 듣는다.

> "어? 내 컴퓨터에서는 안 돼!"

내 컴퓨터에는 게임이 필요한 프로그램(파이썬 3.12, 여러 도구)이 깔려 있었지만, 친구 컴퓨터에는 없거나 버전이 달랐기 때문이다. 이런 일을 "내 컴퓨터에서는 되는데요?" 문제라고 부른다.

**해결 방법**: 게임만 보내지 말고, **게임이 돌아가는 데 필요한 것을 전부 한 상자에 담아서** 보낸다. 이 상자가 컨테이너다. 상자 안은 어디서 열어도 똑같다.

## 2. 컨테이너 = 이삿짐 컨테이너 + 아파트 방

### 이삿짐 컨테이너
배에 실리는 컨테이너는 안에 무엇이 들었든 크기와 모양이 같아서, 어느 배나 트럭에 실어도 문제없이 옮길 수 있다. 소프트웨어 컨테이너도 같다. 안에 든 앱이 파이썬이든 자바든, 컨테이너로 포장하면 **어디서나 같은 방식으로 실행**된다.

### 아파트 방
컨테이너를 **아파트의 각 집**이라고 생각하면 된다.

- 집마다 문이 따로 있고, 옆집이 뭘 하는지 안 보인다 → **서로 격리**된다
- 하지만 건물의 수도관과 전기 시설은 같이 쓴다 → **컴퓨터의 핵심 부분(커널)을 공유**한다
- 그래서 집을 새로 짓는 것보다 훨씬 빨리, 가볍게 만들 수 있다

| | 가상 머신(VM) | 컨테이너 |
|---|---|---|
| 비유 | 단독주택 (집마다 수도관, 전기 설비까지 따로 지음) | 아파트의 한 집 (설비는 건물이 공유) |
| 만드는 시간 | 오래 걸림 | 순식간 |
| 크기 | 큼 | 작음 |

## 3. 이미지와 컨테이너 = 밀키트와 완성된 요리

| 도커 용어 | 비유 | 설명 |
|---|---|---|
| **이미지** | 밀키트 (재료 + 만드는 법이 담긴 상자) | 읽기만 가능한 설계도. 열지 않으면 아무 일도 안 일어난다 |
| **컨테이너** | 밀키트로 만든 요리 | 이미지로 만든, 지금 실제로 돌아가는 것 |
| **Dockerfile** | 요리 설명서 | "이 순서대로 밀키트를 만들어라"라고 적은 글 |
| **Docker Hub** | 밀키트 가게 | 남들이 만든 이미지를 받아 오는 곳 (`docker pull`) |

- 밀키트 하나로 요리를 **여러 번, 여러 접시** 만들 수 있다. 이미지 하나로 컨테이너를 여러 개 띄울 수 있다 (Day 2에서 `hello`, `hello2`를 띄웠다)
- 요리를 먹어 치워도 밀키트는 그대로 있다. 컨테이너를 지워도 이미지는 남는다
- 이미 만든 요리의 맛을 바꾸려면 밀키트를 새로 만들고 요리도 새로 해야 한다. 이미지를 새로 빌드해도 **이미 돌고 있는 컨테이너는 안 바뀐다** (Day 2 실습 4)

## 4. 레이어 = 케이크 층, 캐시 = 만들어 둔 층 재사용

이미지는 **여러 층을 쌓은 케이크**와 같다.

```
맨 위   ← 내 앱 파일 복사 (COPY)       얇은 층, 자주 바뀜
        ← 작업 폴더 만들기 (WORKDIR)
        ← 파이썬 설치                  두꺼운 층
맨 아래 ← 리눅스 기본 (Debian)         가장 두꺼운 층
```

- 케이크를 다시 만들 때 **바뀐 층 아래만** 새로 굽고, 안 바뀐 층은 지난번 것을 그대로 쓴다. 이게 **빌드 캐시**다. 빌드 출력의 `CACHED`가 "그 층은 지난번 걸 재사용했다"는 뜻이다
- 자주 바뀌는 층(내 코드)을 **위쪽에** 두면 아래의 두꺼운 층은 재사용해서 빠르다 (Day 2 `docker history`에서 내 층은 4.1kB, 베이스는 100MB 넘었다)
- 같은 층을 쓰는 이미지끼리는 **층을 공유**해서 디스크를 아낀다

## 5. 컨테이너는 "일회용 접시"

컨테이너를 지우면 **안에 만든 파일도 같이 사라진다**. Day 3 실습 1에서 DB에 테이블을 만들었다가 컨테이너를 지우고 다시 만들자 테이블이 없었다.

- 이유: 컨테이너의 쓰기 공간은 이미지 위에 얹은 **임시 메모장**이기 때문이다
- 그래서 남겨야 하는 것은 컨테이너 **밖**에 보관한다

## 6. 볼륨과 바인드 마운트 = 사물함과 공유 책상

| | 비유 | 이럴 때 |
|---|---|---|
| **네임드 볼륨** | 학교 **사물함** (선생님(도커)이 관리하는 보관함) | 컨테이너가 만든 데이터를 지켜야 할 때 (DB 파일) |
| **바인드 마운트** | 내 방 **책상을 교실로 그대로 연결**한 것 | 내가 고친 파일이 컨테이너에 바로 보여야 할 때 (코드, 웹 페이지) |

- 사물함에 넣은 물건은 교실(컨테이너)이 없어져도 남는다 → Day 3 실습 2에서 컨테이너를 지워도 테이블이 남았다
- 책상을 연결하면 내가 쓴 글이 교실에서 **바로** 보인다 → 실습 3에서 `bind mount`가 `changed`로 바로 바뀌었다
- 책상에 `:ro`(읽기 전용) 표시를 하면 교실에서는 보기만 하고 못 고친다

## 7. 포트 = 건물 호수

컴퓨터 한 대에는 앱이 여러 개 돌 수 있어서, 요청이 **어느 앱으로 갈지** 알려주는 번호가 포트다. 건물의 호수와 비슷하다.

`-p 8081:80`은 이런 안내문이다.

> "**내 컴퓨터의 8081번 문**으로 오는 손님을 **컨테이너 안 80번 방**으로 안내해 줘"

```
내가 접속: localhost:8081  →  [내 컴퓨터 8081번 문]  →  [컨테이너 80번 방] nginx
```

- 앞 번호는 **내 컴퓨터**에서 쓰는 번호라서 다른 프로그램과 겹치면 안 된다 (Day 3에서 8080이 이미 쓰여서 8081로 바꿨다)
- 뒤 번호는 컨테이너 **안**의 번호라서, 앱이 정한 대로 둔다

## 8. 네트워크 = 같은 반 아이들

컨테이너끼리 이야기하려면 같은 **네트워크**에 있어야 한다.

- **기본 네트워크 (bridge)**: 이름표 없는 복도. 번호(IP)를 알아야만 부를 수 있다
- **내가 만든 네트워크 (mynet)**: **같은 반**. 이름표가 있어서 "server야!" 하고 이름만 불러도 선생님(내장 DNS)이 번호를 찾아 연결해 준다

번호(IP)는 컨테이너를 새로 만들 때마다 바뀔 수 있지만 이름은 그대로다. 그래서 **이름으로 부르는 방식이 실무에서 중요**하다. 다른 반(다른 네트워크) 아이들끼리는 서로 안 보여서 프로젝트별로 나눌 수도 있다.

## 9. 한눈에 보는 전체 그림

```
Docker Hub (밀키트 가게)
     │ docker pull
     ▼
  이미지 (밀키트) ◀── docker build ── Dockerfile (요리 설명서)
     │ docker run
     ▼
 컨테이너 (요리) ──┬── 볼륨 (사물함): 데이터 보관
                   ├── 포트 -p (건물 호수): 바깥에서 접속
                   └── 네트워크 (같은 반): 다른 컨테이너와 대화
```

## 10. 용어 사전

| 용어 | 한 줄 설명 |
|---|---|
| 컨테이너 | 앱과 필요한 것을 담은 격리된 실행 상자 |
| 이미지 | 컨테이너를 만드는 읽기 전용 설계도 |
| Dockerfile | 이미지를 만드는 순서를 적은 파일 |
| 레이어 | 이미지를 이루는 한 겹. 안 바뀌면 재사용 |
| 레지스트리 | 이미지를 보관하고 나눠 주는 곳 (Docker Hub) |
| 커널 | 운영체제의 핵심. 컨테이너들이 함께 쓴다 |
| 볼륨 | 컨테이너 밖에 데이터를 보관하는 도커 관리 저장소 |
| 바인드 마운트 | 내 컴퓨터의 폴더를 컨테이너에 그대로 연결 |
| 포트 매핑 | 내 컴퓨터 번호와 컨테이너 번호를 이어 주는 것 (`-p`) |
| 사용자 정의 네트워크 | 이름으로 서로 부를 수 있는 컨테이너 모임 |
